Chapter 01

Computer Science Foundations & Network Theory

1.1 What is Web Engineering?

Web engineering is the application of systematic, disciplined, and quantifiable approaches to the development, operation, and maintenance of high-performance web applications. Modern web engineering is divided into two operational halves:

  • Frontend (Client-Side Engineering): Executed inside the user's browser (Google Chrome, Safari). It is responsible for rendering graphical interface elements (UI), capturing user interactions (UX), managing client state, and ensuring smooth performance at 60 frames per second. Technologies: HTML5, CSS3, JavaScript ES6+, React 18, Vite.
  • Backend (Server-Side Engineering): Executed on remote cloud infrastructure. It handles business logic, security authentication, database transactions, API routing, data validation, and asynchronous event streams. Technologies: Java 17, Spring Boot 3, Spring Cloud Gateway, Apache Kafka, PostgreSQL/H2.
🔬 Deep Theoretical Dive: How the Internet Transfers Data (TCP/IP & HTTP)

When a user opens FlavorDash in their browser, a multi-step networking handshake takes place across the 7 Layers of the OSI Model:

  1. DNS Resolution (Domain Name System): The browser queries a DNS server to translate a human-friendly hostname (e.g. flavordash.com) into a machine IP address (e.g. 192.0.2.1).
  2. TCP 3-Way Handshake: The client and server establish a reliable connection over Transmission Control Protocol using three signals: SYN ➔ SYN-ACK ➔ ACK.
  3. TLS Encryption (HTTPS): A TLS (Transport Layer Security) handshake encrypts data using public-key cryptography to prevent eavesdropping.
  4. HTTP Request/Response Cycle: The client sends an HTTP request containing a Method, Path, Headers, and optional Body. The server processes the request and returns an HTTP Response with a Status Code (e.g. 200 OK, 201 Created, 404 Not Found, 500 Internal Error).

1.2 HTTP Methods & RESTful Principles

Representational State Transfer (REST) is an architectural style for designing networked applications. It relies on standard HTTP methods:

HTTP Method Purpose / Action Idempotent? FlavorDash Example
GET Retrieve data without altering server state. ✅ Yes GET /api/products (Fetch dish catalog)
POST Create a new resource on the server. ❌ No POST /api/users/register (Register user)
PUT Replace/update an existing resource entirely. ✅ Yes PUT /api/orders/101 (Update order status)
DELETE Remove a resource from the server database. ✅ Yes DELETE /api/cart/item/5 (Remove cart item)

Software Architectural Paradigms: Monolith vs Microservices

2.1 Monolithic Architecture

In a traditional Monolithic Architecture, all functional modules of an application (User Management, Food Catalog, Order Processing, Payment Processing, Kitchen Notifications) are compiled and packaged into a single deployable unit (e.g., a single 500MB .jar file or .war file).

⚠️ The Monolith Bottleneck in Food Delivery Systems

Consider a high-traffic lunch hour (12:00 PM - 2:00 PM). Millions of hungry customers are opening the app to view menus. This causes massive CPU spikes on the Product Catalog component. In a monolith:

  • You must scale the entire application, including the Payment and User modules which don't need scaling.
  • If a memory leak or crash occurs in the Payment module, the entire monolith crashes—preventing users from even viewing menus!

2.2 Microservices Architecture (FlavorDash Design)

In FlavorDash, we decomposed the application into 7 independent, loosely-coupled microservices. Each microservice runs as its own standalone process on its own designated port:

Microservice Name Port Specific Business Responsibility Database Isolation
Config Server 8888 Centralized native YAML config storage across environments. YAML Config Store
Eureka Discovery Server 8761 Dynamic Service Registration & Health Heartbeat Checking. In-Memory Registry
API Gateway 8080 Unified Entry Gateway, CORS Filter, Reactive Traffic Forwarding. Stateless Router
User Service 8081 User Registration, Profile Management, Role Security (Customer/Hotel/Rider). User DB (H2/PostgreSQL)
Product Service 8082 Food Items Catalog, Pricing, Veg/Non-Veg Badges, Dietary Metadata. Product DB (H2/PostgreSQL)
Order Service 8083 Cart Checkout Processing, Order Lifecycle, OpenFeign Client integration. Order DB (H2/PostgreSQL)
Payment Service 8084 Payment Gateway processing, Mock UPI QR generation & Kafka consumer. Payment DB (H2/PostgreSQL)

Spring Boot 3 Backend Microservices Deep Dive

4.1 Spring Boot Core Concepts

Spring Boot simplifies Java enterprise application development by eliminating complex XML configurations in favor of sensible auto-configuration and Java-based annotations.

Key Annotations Used in FlavorDash Code:

  • @SpringBootApplication: Master annotation that enables Component Scanning (@ComponentScan), Auto-Configuration (@EnableAutoConfiguration), and Configuration definition (@Configuration).
  • @RestController: Combines @Controller and @ResponseBody. Instructs Spring to serialize method return values directly into JSON HTTP responses.
  • @RequestMapping("/api/products"): Defines the base URI path for all endpoints in a controller class.
  • @GetMapping / @PostMapping: Maps specific HTTP GET and POST requests to Java methods.
  • @PathVariable: Extracts path variables from URIs (e.g. /api/products/{id} ➔ Long id).
  • @RequestBody: Deserializes incoming HTTP JSON payload into Java DTO objects.
  • @EnableEurekaServer: Activates Eureka Discovery Registry on port 8761.
  • @EnableFeignClients: Enables declarative HTTP web client interfaces for inter-service communication.

4.2 Code Structure of a FlavorDash Microservice

Each microservice follows the clean 3-Tier Layered Architecture:

src/main/java/com/fooddelivery/product/
├── ProductServiceApplication.java   # Main Entry Class (@SpringBootApplication)
├── controller/
│   └── ProductController.java       # Controller Layer (Handles HTTP REST Endpoints)
├── service/
│   └── ProductService.java          # Service Layer (Business Logic & Rules)
├── repository/
│   └── ProductRepository.java       # Data Access Layer (Spring Data JPA Interface)
├── model/
│   └── Product.java                 # Entity Class (@Entity - Database Schema Mapping)
└── dto/
    ├── ProductRequest.java          # Data Transfer Object for Request Payload
    └── ProductResponse.java         # Data Transfer Object for Clean JSON Output

4.3 Inter-Service Communication via OpenFeign

When a user places an order in Order Service, it needs to verify if the user exists in User Service and fetch dish prices from Product Service. Instead of writing boilerplate RestTemplate code, we use Spring Cloud OpenFeign:

// Order Service Client Interface
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/api/users/{id}")
    UserResponse getUserById(@PathVariable("id") Long id);
}
Chapter 05

Apache Kafka & Event-Driven Architecture

5.1 What is Event-Driven Architecture (EDA)?

In traditional REST architectures, services call each other synchronously and wait for responses. If service B is slow or down, service A blocks. In Event-Driven Architecture, services communicate by publishing and listening to asynchronous messages (events) over an Event Bus like Apache Kafka.

5.2 Apache Kafka Key Components

  • Producer: The service that creates and publishes an event message (e.g. Order Service emitting ORDER_CREATED).
  • Topic: A named logical stream or log where Kafka stores messages (e.g. order-events-topic).
  • Consumer: The service that subscribes to a topic and processes incoming messages asynchronously (e.g. Payment Service consuming ORDER_CREATED).
  • Broker: The Kafka server instance that stores topics and handles event delivery.
🔄 Real-World FlavorDash Event Flow
  1. User clicks "Place Order" on Frontend.
  2. Order Service saves order in database as PENDING.
  3. Order Service Producer publishes OrderEvent payload to Kafka topic order-topic.
  4. Payment Service Consumer immediately receives OrderEvent message, triggers payment processing, and saves payment transaction.
  5. Payment Service Producer publishes PaymentEvent back to Kafka topic payment-topic.
  6. Order Service Consumer listens to payment-topic and updates order status to CONFIRMED.

Databases & Data Persistence

7.1 Relational Databases & Spring Data JPA

Java Persistence API (JPA) is a specification for Object-Relational Mapping (ORM) in Java. It allows developers to interact with SQL database tables using pure Java Objects (Entities) without writing manual SQL queries.

@Entity
@Table(name = "products")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    
    private String name;
    private Double price;
    private String category;
    private Boolean isVeg;
}

8.2 Containerized Backend Deployment on Render.com

Each Spring Boot microservice contains a production multi-stage Dockerfile. Multi-stage builds keep container images small by separating the Maven compilation stage from the runtime stage:

# Stage 1: Build JAR using Maven
FROM maven:3.9.6-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Minimal Java Runtime
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Question 02
Why did you choose Microservices Architecture over a Monolith?
"In a food delivery domain, different functional domains experience radically different traffic patterns. Product catalog browsing occurs millions of times per hour, whereas Payment transactions occur only at checkout. With microservices: 1) We can scale Product Service independently without wasting resources on Payment Service, 2) We achieve Fault Isolation—if Payment Service experiences a temporary slowdown, users can still browse food menus uninterrupted, and 3) Teams can develop and deploy services independently."
Question 03
What is the role of API Gateway in your architecture?
"The API Gateway running on port 8080 serves as the single entry portal for all incoming client traffic. Instead of the browser making direct requests to 7 different ports, it talks only to port 8080. The Gateway handles path routing (mapping /api/products to Product Service), CORS configuration, and central security checks before requests reach internal microservices."
Question 04
How does Service Discovery with Netflix Eureka work?
"Eureka Server running on port 8761 acts as a dynamic service directory. When each microservice boots up, it sends its IP address, port, and health heartbeat to Eureka. When the API Gateway needs to forward a request to product-service, it asks Eureka for the live network coordinates dynamically, eliminating hardcoded IP addresses."
Question 05
How do microservices communicate synchronously vs asynchronously?
"For synchronous queries requiring immediate responses (e.g. Order Service fetching dish details during checkout), we use Spring Cloud OpenFeign interfaces. For asynchronous, non-blocking events (e.g. Order Created or Payment Completed notifications), we use Apache Kafka event streams."
Question 06
How did you handle security and Role-Based Access Control (RBAC)?
"User profiles carry a role tag (`CUSTOMER`, `HOTEL_MANAGER`, `RIDER`). On the frontend, React Router uses a custom `` component. If an unauthorized user attempts to access `/kitchen` or `/driver`, the guard intercepts the request and redirects to Home with an Access Denied alert."
Question 07
What is Dependency Injection in Spring Boot?
"Dependency Injection (DI) is a design pattern where the Spring IoC (Inversion of Control) container automatically creates and injects required objects (like Repositories or Services) into classes via `@Autowired`, reducing hardcoded dependencies and making code easy to unit test."
Question 08
What is the difference between JPA and Hibernate?
"JPA (Java Persistence API) is a standard Java specification or interface definition for object-relational mapping. Hibernate is the actual concrete underlying framework implementation that executes the ORM queries against SQL databases."
Question 09
How did you structure state management in React?
"We used React Context API (`AuthContext` for user session & roles, `CartContext` for cart state) for app-wide global state, and local `useState` for component-level UI interactions (e.g., active filters or modal visibility)."
Question 10
What are Docker multi-stage builds and why did you use them?
"Multi-stage Docker builds use multiple `FROM` instructions in a single Dockerfile. Stage 1 compiles the Java code using a heavy Maven image. Stage 2 copies only the final built `.jar` file into a tiny, lightweight Alpine JRE runtime image, reducing container size from 600MB down to 150MB for cloud deployment."
